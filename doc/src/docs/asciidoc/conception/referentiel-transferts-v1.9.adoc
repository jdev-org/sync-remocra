== Objet

Cette page est la transcription technique du classeur
`additionnel/Referentiel_Transferts__EDP-BSPP_V1.9.xlsx`, pour les feuilles dont le nom commence
par `CIBLE -` :

* `CIBLE - Transfert VISITES` ;
* `CIBLE - Transferts liés à AE`.

Elle fixe l'ordre de réalisation futur : *une ligne du référentiel est un cas de développement,
un test automatisé et un commit distinct*, après validation du métier et des codes REMOcRA par
ATOL CD/BSPP. Elle ne modifie pas le comportement de l'application.

Les colonnes `J` et `K` de la feuille des visites ne constituent pas à elles seules un contrat API :
le type de visite est renseigné, mais plusieurs codes d'anomalie restent à définir. La colonne
`R - PROPOSITIONS BSPP / VDP` est vide dans la version V1.9 reçue.

== Légende de faisabilité

|===
|Statut |Signification

|Conforme sous réserve de la vue
|Le push-worker sait construire le payload attendu si la vue Oracle produit le déclencheur et le
`type_derniere_visite` indiqués.

|Écart applicatif
|Le comportement actuel diffère de la cible : une évolution du changedatacapture et/ou du
push-worker sera nécessaire.

|Bloqué par le référentiel
|Un code REMOcRA, le tableau cible (`anomaliesConstatees` ou `anomaliesControlees`), une

clarification.

|Incohérence à arbitrer
|Les cellules d'une même ligne ou de plusieurs lignes expriment des résultats incompatibles. Le
métier doit confirmer la règle attendue avant implémentation.
|===

== Identifiants provisoires des anomalies à créer

En attente des codes officiels ATOL CD/BSPP, les cas qui ne disposent pas d'un code d'anomalie
validé sont repérés par un identifiant technique unique. Cet identifiant permet de nommer sans
ambiguïté le test, le commit et la règle de code de chaque ligne.

Il *ne doit jamais être placé dans un payload REMOcRA*. Lors de la validation d'un code officiel,
l'identifiant provisoire sera remplacé dans la documentation, les tests et le code par ce code
officiel. Les lignes disposant déjà d'un code (`BSPP_APDP`, `BSPP_APSE`, `BSPP_BISD` ou
`BSPP_PISD`) n'ont pas d'identifiant provisoire.

== Chaîne de responsabilité

. WATGIS ou SmartMobility produit une action de clôture, des mesures ou une modification d'arrêt
  d'eau.
. Les vues Oracle exposent les données et une date de changement. Elles choisissent notamment le
  déclencheur `date_maj_qp`, `date_maj_cf`, `date_maj_np`, `date_maj_mj` ou `date_maj_e`.
. Le changedatacapture copie la ligne de vue dans la traçabilité et crée un message local. Il ne
  traduit pas les libellés de clôture.
. Le push-worker choisit le service REST, construit le payload et appelle REMOcRA.
. REMOcRA applique ses règles sur les points d'attention et déduit l'état opérationnel du PEI.

Les règles qui demandent qu'un contrôle périodique aboutisse en `NP` imposent donc que la vue
fournisse `date_maj_np` et un `type_derniere_visite` commençant par `NP`, ou qu'une évolution
explicite de la passerelle soit validée. Aujourd'hui, une ligne `PIQP` devient `CTP` et une ligne
`PICF` devient `CTP`.

=== Saisie manuelle de mesures, ligne 57

Une modification des valeurs Q/P, qu'elle provienne de SmartMobility ou de WatGIS, doit modifier
`date_maj_mj`, créer un message `MANUELLE`, puis envoyer une visite `NP` avec `pression`,
`pressionDynamique` et `debit`.
La cible demande que REMOcRA applique son anomalie de pression dynamique insuffisante lorsque la
valeur est inférieure à 1 bar ou 60 m3/h.

Le transport des mesures est *conforme*. La passerelle ne calcule pas ce seuil et n'ajoute pas
elle-même de point d'attention : cette règle relève de REMOcRA ou nécessite une règle explicitement
attribuée à Sync-remocra.

=== Mise à jour patrimoniale, ligne 58

La ligne 58 est une cible `CARACTERISTIQUES`, et non une visite. Une modification patrimoniale
doit modifier `date_maj_p`, créer un message `CARACTERISTIQUES`, puis déclencher le push-worker.
Celui-ci identifie la nature `PIBI` ou `PENA` et transmet, selon le cas, les informations de
diamètre, canalisation, PEI jumelé, marque, modèle, réseau et canalisation au service de
caractéristiques REMOcRA.

Cette cible est décrite dans
link:pushworker/caracteristiques-v3.html[la conception des caractéristiques REMOcRA V3]. Toute
nouvelle colonne de vue ou règle de correspondance doit être ajoutée à cette page avant évolution.

== Préparation des développements ligne par ligne

Chaque évolution future devra respecter la séquence suivante :

. confirmer la ligne du référentiel, notamment le code BSPP, le type de visite et les deux tableaux
  d'anomalies ;
. identifier si la vue Oracle fournit déjà le déclencheur et le libellé nécessaires ;
. implémenter le plus petit changement factorisé dans le changedatacapture ou le push-worker ;
. ajouter un test unitaire couvrant le payload complet et, lorsque nécessaire, le message créé ;
. mettre à jour cette page avec le statut « implémenté » et le numéro de version ;
. obtenir la validation métier sur cette seule ligne avant le commit suivant.

Les règles existantes qui ne sont pas listées dans le classeur V1.9 seront inventoriées après la
mise en oeuvre de toutes les lignes cibles. Elles ne doivent pas être supprimées ni modifiées sans
une décision métier explicite.
